Schedule

Three days, 20 contact hours in two-hour blocks. Breaks and lunch are not counted as contact time.

The course runs on one Sunday in November and one weekend in January, with seven weeks in between. Each class takes two blocks. The first block opens with a recap of the class page, which you read beforehand, and starts the build lab. The second block finishes the lab, then two teams show their work for critique and the milestone review closes the class.

Teams of 2 or 3 form on Day 1 around a problem from one member’s organization. The capstone is one application, and each class adds a layer to it.

Class The product gains New building block
1 A deployed app and a public web page Prompts and the brief
2 Login, a database, rollback Project instructions, one skill, one connector
3 An AI capability with a test set One agentic step with approval, one automation
4 Fixed security findings and a decision Least-privilege permissions

Day 1, Sunday 29 November 2026

Class 1. Ship something today

Class page: Class 1 · Ship something today

Build goal. A deployed web application that a real user could open on a phone, and a one-page public site that explains it.

Before Day 1. Read the class page (90 min). Create a GitHub account. Read Karpathy’s original post on vibe coding and Willison’s “Not all AI-assisted programming is vibe coding” (20 min). Bring one problem from your organization in which people enter, read or act on information by hand, and a laptop on which you can install programs.

08:00 to 10:00. Framework recap (45): what changed in the cost of building software; the toolkit map; vibe coding versus AI-assisted engineering; Problem Pull versus AI Push; the one-paragraph brief. Then the build lab starts with the instructor’s live demo, which includes a bug and its recovery, and teams begin their own first version (75).

10:15 to 12:15. The build lab continues until the app is deployed and open on a phone, and the public page is up (45). Critique: two teams show their app and the class applies the rubric (45). Milestone review: M1 explained, teams confirmed (30).

Setup clinic

12:30 to 14:30. The toolkit setup guide done in the room, with the instructor walking between tables: the remaining accounts, the app moved to a private repository, the assistant running it on every member’s laptop, the database project, the hosting address, and where keys go (90). Then the M1 brief is started in teams (30). Everyone leaves Day 1 with a working setup, so the seven weeks ahead depend on nobody’s luck.

Day 2, Saturday 16 January 2027

Class 2. Specify, iterate, keep what works

Class page: Class 2 · Specify, iterate, keep what works

Build goal. The application stores data for signed-in users and has a version history you can roll back, and the team’s assistants know how the team works: project instructions, one skill and one read-only connector.

08:00 to 10:00. Framework recap (45): prompting as specification; small steps, checkpoints and rollback; where the data lives; UX for output that is sometimes wrong; the three things people call “the AI”; project instructions and skills; connectors and the Model Context Protocol. Then the live demo and the first part of the build lab: the database and sign-in, as two separate requests with two checkpoints (75).

10:30 to 12:30. The build lab continues: a deliberate rollback, two UX patterns, the project instructions file, one skill that triggers, one read-only connector (45). Critique: two teams show a user story end to end and their skill being used; rubric criterion in focus, functionality (45). Milestone review: feedback on M1, briefing for M2 (30).

Class 3. Add intelligence, then prove it works

Class page: Class 3 · Add intelligence, then prove it works

Build goal. The application uses a language model for one capability that matters to the user, the team can show a test set with results before and after a guardrail, and one step runs either as an agent that waits for approval or as a scheduled automation.

14:00 to 16:00. Framework recap (45): what a model call costs; four patterns that cover most business cases; retrieval over company documents; agents and the three levels of autonomy; automations with owners, logs and limits; test sets. Then the live demo and the first part of the build lab: the products table, the model connected the right way, the AI feature deployed and tested at the public address (75).

16:30 to 18:30. The build lab continues: the test set run before and after a guardrail, then one of two, the agentic step with approval or the morning digest (45). Critique: pass rates before and after the guardrail; rubric criterion in focus, AI quality and safety (45). Milestone review: M2 checked, M3 explained, Day 3 explained (30).

After 18:30. The product is frozen: no new features until Demo Day. On Day 3 you only fix security findings. M2 is the state of your repository at the end of Day 2; submit the link and each member’s build log by 23:59.

Day 3, Sunday 17 January 2027

Class 4. Govern what you built

Class page: Class 4 · Govern what you built

Build goal. No leaked secrets, authorization enforced, the assistants’ permissions as small as the job allows, personal data handled deliberately, the monthly cost known, and the build / buy / vibe decision made: keep vibe coding it, hand it to engineering to build properly, buy a product, or stop.

08:00 to 10:00. Framework recap (30): secrets, authorization, prompt injection, permissions, personal data under Ley 21.719, cost at scale, maintainability. Then the build lab (90), which opens with the security checklist run on your own app in the room and goes on to fix what it finds.

10:15 to 10:45. The build lab ends with the cost at 10x and 100x and the build / buy / vibe decision (30). In this format Class 4 has no separate critique block: the questions an engineering team would ask go into your risk memo.

Class 5. Demo Day and strategy revisited

Class page: Class 5 · Demo Day and strategy revisited

10:45 to 11:15. Pitch clinic. Teams generate the deck with AI from their own sources (build log, test results, the morning’s security findings, cost figures), check every number against its source, and do one timed run of ten minutes.

11:15 to 13:30. Demo Day (120 minutes, with the coffee break at 12:15). Each team has 10 minutes plus 5 of questions in front of a panel (the instructor and two invited managers or alumni): a live demonstration with a user story, the problem and the baseline of the metric, evidence from the test set, the main security findings, the build / buy / vibe decision and a roadmap to production. The deck is generated with AI and its use is declared. The time fits eight teams; with more teams, the strategy block shortens.

13:30 to 14:00. Strategy revisited. What remains a moat when building is cheap; citizen developers and how an organization governs them; the personal AI work system you keep after the course.

14:00 to 14:30. Reflection. The reflection memo is started from the build log (20) and teams complete the peer assessment (10).

Everything is graded with the rubric. Written work is due at 23:59 on the day shown.

The data rule. Until your team has completed the Class 4 lab, closed every critical finding, and has the written agreement of the organization that owns the data, use only invented or de-identified information: no real names, phone numbers, addresses or tax numbers. Most teams will stay with de-identified data through Demo Day, and that costs nothing in the grade.

Work outside class. The class pages take 90 to 100 minutes each, the milestones about 8 hours in total, and Demo Day preparation about 7 hours, most of it in the weeks between Day 1 and Day 2.
