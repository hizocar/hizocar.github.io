1 · Demostración en vivo

De una carpeta vacía a una página en el celular en unos diez minutos. Mira el orden, no los clics: describir, planificar, leer, construir, mirar, un cambio, publicar. Lo repites todo el día.

2 · Revisión de instalación

Abre una terminal (en VS Code: Terminal → New Terminal) y corre las cinco pruebas de la guía de instalación. Escribe una línea, presiona Enter, lee la respuesta y pasa a la siguiente.

Prueba Pasa cuando
1. code --version muestra un número
2. git config --global user.email muestra el correo de tu cuenta de GitHub
3. node -v muestra v22 o superior
4. claude, luego dentro /status, luego /exit aparece tu cuenta de Claude
5. El panel el ícono Spark (✻) o ✻ Claude Code en la barra de estado, abajo en VS Code, abre el panel de Claude Code

Si una prueba falla, la guía de instalación tiene la solución. Si después de diez minutos sigue fallando, siéntate con un vecino y trabajen en pareja en su notebook hasta el café; el profesor arregla el tuyo en ese momento.

Luego crea la carpeta de tu proyecto, aquí llamada mi-web: elige tu propio nombre, en minúsculas, sin espacios ni tildes. Va en Proyectos, fuera del Escritorio, Documentos, iCloud, OneDrive o Google Drive, que sincronizan archivos mientras Claude los escribe.

En la terminal · Mac
mkdir -p ~/Proyectos/mi-web && code ~/Proyectos/mi-web
En la terminal · Windows
mkdir $HOME\Proyectos\mi-web; code $HOME\Proyectos\mi-web

Se abre una nueva ventana de VS Code con la carpeta vacía. Abre el panel desde ✻ Claude Code en la barra de estado de abajo (o ⌘/Ctrl + Shift + P, escribe Claude Code y elige el comando que lo abre). No crees ningún archivo tú: la carpeta debe quedar vacía hasta que Claude cree el proyecto. Claude trabaja dentro de la carpeta que abriste: no ve el resto de tu computador salvo que se lo permitas.

Práctica · Cómo funciona

Claude dice que tu formulario de contacto "ya funciona". ¿Qué haces ahora?

Que suene bien no significa que sea cierto. Juzgar el resultado usándolo es tu parte del ciclo, y es la parte que nadie puede hacer por ti.

Después de dos horas en la página de inicio empiezas la presentación en la misma conversación, y Claude se pone lento y confuso. ¿Por qué?

La ventana de contexto es memoria de trabajo. Una tarea nueva merece una ventana limpia; lo que debe perdurar va en CLAUDE.md.

Claude pide permiso para ejecutar rm -rf ~/Documents/old. ¿Cuál es la respuesta correcta?

rm, sudo, un push forzado o cualquier cosa fuera de tu carpeta: detente y pregunta. Un agente con tus permisos puede hacer todo lo que tú puedes.

Los 75 minutos del laboratorio. El paso más largo es esperar mientras Claude construye: lee cada permiso y no empieces otra cosa mientras tanto.

Lo que construyes en los próximos 75 minutos

Solo, sobre tu propia idea. El profesor recorre la sala. Si llevas más de cinco minutos atascado, levanta la mano.

  1. Abre tu brief (2 min). Las cinco líneas que escribiste en casa: cuál es tu idea, para quién es, la única cosa que debe hacer quien visite, cómo debe sentirse (dos sitios que te gusten) y lo que no quieres. ¿No tienes brief? Escríbelo ahora, cinco líneas.
  2. Pasa a modo plan y envía el primer prompt (5 min). Usa el prompt de abajo con tu brief dentro.
  3. Responde sus preguntas y lee el plan (10 min). Si el plan agrega cosas que no pediste, como un inicio de sesión, un blog o una base de datos, dile: "Quita X por ahora; la primera versión se limita al brief." Aprueba cuando calce.
  4. Déjalo construir, leyendo cada permiso (18 min). Crear un proyecto Next.js descarga mucho y pide varios permisos. Con el wifi compartido es lento: ten paciencia y no empieces otra tarea mientras tanto.
  5. Ábrela (5 min). Pide: "Levanta el servidor de desarrollo y dame la URL." Abre http://localhost:3000. Esa es tu web, visible solo en tu notebook. Se actualiza sola cada vez que Claude cambia un archivo.
  6. Pruébala como un visitante (10 min). Léela como la leería tu público. Revisa cada afirmación que Claude escribió sobre tu negocio: precios, promesas, cifras, nombres. Inventa algunas que suenan creíbles; quita lo que no sea cierto. Luego angosta la ventana del navegador, como un celular. Anota las tres cosas que menos te gustan.
  7. Un cambio a la vez (15 min). Arregla esas tres cosas, un prompt cada una, mirando la página después de cada cambio.
  8. Vuelve atrás una vez, a propósito (5 min). Pide un cambio que no te guste y luego deshazlo: pasa el mouse sobre tu mensaje en el panel, presiona el botón de rewind y elige Rewind code to here (volver el código a este punto). (En la terminal, /rewind o Esc dos veces.) Así sales de un camino equivocado en segundos.
  9. Guarda tu avance (5 min). Pide: "Haz commit de todo con el mensaje 'primera versión'." Un commit es una foto guardada del proyecto, a la que siempre puedes volver.
Tú, a Claude · el primer prompt (en modo plan)
Quiero crear la web de [mi idea, en una frase]. Objetivo: [la única cosa que debe hacer quien visite: escribirme, agendar una llamada, inscribirse en la lista]. Público: [quiénes son], que leen sobre todo en el celular. Estilo: [dos o tres adjetivos]. Sitios que me gustan: [uno o dos links]. Evita: [lo que no quieres]. Secciones: [tres a cinco secciones]. Usa Next.js con Tailwind, lista para publicar en Vercel. Crea el proyecto directamente en esta carpeta, no en una subcarpeta. Todavía sin base de datos ni inicio de sesión. Antes de escribir código, hazme las preguntas que necesites y propón un plan.
Tú, a Claude · un cambio
Un solo cambio, nada más: [lo que quieres, lo más preciso posible, por ejemplo: el título es muy largo, déjalo en menos de ocho palabras sin perder el sentido]. Deja todo lo demás como está. Cuando termines, dime en una frase qué cambiaste.
Tú, a Claude · cuando algo se ve mal
En una ventana del tamaño de un celular, [exactamente lo que ves, por ejemplo: el menú tapa el título y no lo puedo cerrar]. En una ventana ancha se ve bien. Primero explícame en palabras simples qué crees que está pasando. Luego arréglalo y dime cómo comprobarlo.

Describe lo que ves, no lo que crees que debería hacer el código. “El botón no hace nada cuando lo toco” es mejor que “arregla el JavaScript”. Si el mismo error vuelve tres veces, deja de pedir arreglos: presiona Esc, vuelve atrás con rewind hasta antes de que empezara el problema y pide el cambio de otra forma.

Una skill es un manual para un tipo de trabajo. Claude lee solo su lomo, una descripción de una línea, hasta que un pedido calza; entonces lo abre.

Las skills vienen en plugins. Hoy: frontend-design a las 11:30, skill-creator y my-brand a las 13:30.

Instala el plugin de diseño desde el catálogo oficial de Anthropic. Hazlo en la terminal de VS Code, donde el catálogo ya está configurado:

En la terminal de VS Code · escribe claude y luego cada línea dentro, una a la vez
claude /plugin install frontend-design@claude-plugins-official /exit

Vuelve al panel. Si dice Restart Claude to apply plugin changes, hazlo. Escribe /skills para ver lo que tienes ahora; /plugins en el panel los administra. Un plugin puede ejecutar comandos en tu computador: instala solo desde el catálogo oficial o de autores que conozcas, como harías con cualquier programa.

Sube a GitHub (15 min). Dos pasos, en este orden. Primero, pídele a Claude que revise:

Tú, a Claude · antes del primer push
Revisa que nada de lo que voy a subir contenga llaves, contraseñas ni archivos .env, y que todo tenga commit. No hagas push.

Luego, tú: abre Source Control en VS Code (el ícono de ramas a la izquierda, o Ctrl + Shift + G), presiona Publish Branch y elige Publish to GitHub private repository. La primera vez, VS Code te pide iniciar sesión en GitHub en el navegador.

Importa en Vercel (15 min). Entra a vercel.com/new, con tu sesión de GitHub. Busca tu repositorio, presiona Import, no cambies nada, presiona Deploy. En uno o dos minutos tienes una dirección como mi-web.vercel.app. Si tu repositorio no aparece en la lista, elige Adjust GitHub App Permissions, dale a Vercel acceso a todos los repositorios (o a este), guarda y vuelve.

Ábrela en tu celular (5 min). Luego un cambio pequeño: commit, Sync Changes, y Vercel lo publica solo en alrededor de un minuto.

Una regla de proyectos reales: lo que está publicado tiene que estar en GitHub. Commit y push primero, siempre, para que el siguiente deploy automático no deshaga tu trabajo. (Las llaves llegan el Día 2, con sus propias reglas.)

Un deploy fallido no rompe tu web: Vercel mantiene la última versión que funcionó. Revisa Cuando algo sale mal, más abajo.
