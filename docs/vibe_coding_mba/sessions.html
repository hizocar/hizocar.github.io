Session plan

Five 4-hour workshops. One business problem carried from brief to deployed product.

Sessions 1 to 4 follow the same rhythm so students spend their attention on the product, not the format. Session 5 is Demo Day. Each session has an interactive class page, read before class; the full list is in Classes.

Block Minutes What happens
Framework 45 A recap of the class page and questions on it
Build lab 120 Opens with the instructor’s live demo, including one failure and its recovery. Teams then work on their own project toward the session’s build goal, with a 10-minute break
Critique 45 Two teams show their work; the class applies the rubric; reflection prompt in the build log
Milestone review 30 Milestone check-in, feedback on the last deliverable, pre-work for next session

Teams of 2 to 3 form in session 1 around a problem from one member’s organization. The capstone is one application; each session adds a layer to it.

Session The product gains New building block
1 A deployed app and a public web page Prompts and the brief
2 Login, a database, rollback Project instructions, one skill, one connector
3 An AI capability with a test set One agentic step with approval, one automation
4 Fixed security findings, a risk memo, a decision Least-privilege permissions
5 A pitch in front of a panel A deck generated with AI

The data rule. Until your team has completed the session 4 lab, closed every critical finding, and has the written agreement of the organization that owns the data, use only invented or de-identified information: no real names, phone numbers, addresses or tax numbers. Most teams will stay with de-identified data through Demo Day, and that costs nothing in the grade.

Work outside class. Each session asks for the class page (90 to 100 minutes), one short reading (about 20 minutes) and one task. The milestones take about 8 hours in total and Demo Day preparation about 7.

Session 1. Ship something today

Class page: Class 1 · Ship something today

Build goal: a deployed web application that a real user could open in a browser by the end of the session, and a one-page public site that explains it.

Before the session. Read the class page (90 min). Create the accounts in the toolkit setup guide (20 min). Read Karpathy’s original post and Willison’s “Not all AI-assisted programming is vibe coding” (20 min). Bring one business problem from your organization in which people enter, read or act on information.

Framework. What changed in the cost of building software. The toolkit map: which tool and which building block (prompt, project instructions, skill, connector, agent, automation) for which job. Vibe coding versus AI-assisted engineering: where the “vibes” are enough (prototypes, internal tools, tests of demand) and where they are not (regulated, high-volume, safety-critical). Problem Pull versus AI Push. A one-paragraph product brief: user, pain, what the tool does, how we know it works.

Build. The lab opens with the live demo: the instructor builds and deploys a working app from a brief in 20 minutes, including a bug. Teams then choose a problem, write the brief, and build a first version with a conversational app builder. Deploy to a public address. Open it on a phone. Second deliverable: a one-page public site for the product.

Critique. Reflection prompt: what did you expect to be hard that was easy, and vice versa?

Milestone set: M1, individual, due before session 2. A one-page problem brief and product specification (user, pain, value hypothesis, success metric, three user stories with acceptance criteria), written as an instruction to an AI.

Session 2. Specify, iterate, keep what works

Class page: Class 2 · Specify, iterate, keep what works

Build goal: the application stores data for signed-in users and has a version history you can roll back, and the team’s assistants know how the team works: project instructions, one skill and one read-only connector.

Before the session. Submit M1. Read the class page (100 min). Complete the second part of the toolkit setup guide: the app in a private repository, opened in your assistant, with an empty database project and a hosting address (60 min).

Framework. Prompting as specification: the product brief, user stories and acceptance criteria as the contract with the assistant. Working in small steps with checkpoints, branches and rollback. Where the data lives. UX for AI products: non-deterministic output, visible uncertainty, error and loading states. The three things people call “the AI”: the assistant you build with, the assistant a person uses directly, and the model inside the app. Project instructions and skills: packaging “how we do it here”. Connectors and the Model Context Protocol: scoped access to company systems, read before write.

Build. Add the database and sign-in, as two separate requests with two checkpoints. Practice a deliberate rollback: break something, go back. Apply two UX patterns. Write the project instructions file, create one skill and test that it triggers, connect one company source read-only.

Critique. Two teams demonstrate a user story end to end and show their skill being used. Rubric criterion in focus: functionality.

Milestone set: M2, team, due before session 3. Deployed prototype v1 with sign-in and stored data, three working user stories, the project instructions file, one skill, one connector, a private repository, and each member’s build log.

Session 3. Add intelligence, then prove it works

Class page: Class 3 · Add intelligence, then prove it works

Build goal: the application uses a language model for one capability that matters to the user, the team can show a test set with results before and after a guardrail, and one step runs either as an agent that waits for approval or as a scheduled automation.

Before the session. Submit M2. Read the class page (100 min). Read Anthropic, Building effective agents (20 min). Complete “Before session 3” in the toolkit setup guide: the model provider’s account, the spending limit and the key (25 min). Collect 20 to 30 messages your AI feature will receive: real ones with names, phone numbers and addresses changed, or realistic ones you write.

Framework. Language-model APIs for managers: a request, a response, tokens, cost, latency, the context window, choosing a model. Four patterns that cover most business cases: classification, extraction with structured output, summarization, conversational assistant. Retrieval over company documents: when you need it and how it fails. Agents: a model in a loop with tools, and the three levels of autonomy. Automations: triggers, schedules, owners, logs and spending limits. Evaluation: a test set, a success definition, a human in the loop.

Build. Add one language-model capability to the product. Build a test set from the pre-work messages, run it, record results. Add a guardrail and re-run. Then one of two: an agentic step that proposes and waits for approval, or a scheduled automation (for the running case, a morning digest of pending quotes). The other one is homework.

Critique. Teams report the number of tests passed before and after the guardrail. Rubric criterion in focus: AI quality and safety.

Milestone set: M3, team, due before session 5. The AI feature deployed, the test set and results, the guardrail, one agentic step with approval and one scheduled automation, a baseline and one measurement of the brief’s metric on at least five timed requests, and a two-page risk memo (written after session 4).

Session 4. Govern what you built

Class page: Class 4 · Govern what you built

Build goal: the application has no leaked secrets, authorization is enforced, the assistants’ permissions are minimal, personal data is handled deliberately, the monthly cost is known, and the team has made the build / buy / vibe decision.

Before the session. Read the class page (95 min). Run the security checklist on your own app and bring the results (30 min). Skim the OWASP Top 10 for LLM Applications (15 min).

Framework. Security of AI-generated software: secrets, authentication versus authorization, prompt injection in messages and in content returned by connectors. Permissions for skills, connectors and agents: least privilege, approval for consequential actions, third-party skills as a supply chain. Data protection: personal data under Ley 21.719, what vendors do with your data. Cost: token economics, budgets, caching, runaway automations. Maintainability, ownership of generated code and lock-in. The build / buy / vibe decision and its four answers: keep vibe coding it, hand it to engineering to build properly, buy a product, or stop.

Build. Fix the findings of the security checklist with the assistant. Reduce every connector and tool to the least permission that still works. Decide purpose, retention and provider for the personal data you hold. Compute the cost of the AI feature at 10x and 100x current usage. Make the build / buy / vibe decision. The risk memo is written from these results as homework.

Critique. A simulated handoff: one team presents its product to another team acting as the engineering department, which asks the questions from the framework block. Rubric criterion in focus: communication.

Before Demo Day. Finish M3. Read the Class 5 page (90 min). Generate the deck with AI from the build log, the test results and the risk memo (Class 5, topic 1), verify every number, and rehearse once with another team.

Session 5. Demo Day and strategy revisited

Class page: Class 5 · Demo Day and strategy revisited

Block Minutes What happens
Pitch clinic 30 Last check of the deck and the demo against the rubric
Demo Day 150 Each team: 10 minutes plus 5 of questions, in front of the panel
Strategy revisited 30 What remains a moat; from prototype to production
Reflection memo 30 Memo drafted before class and finished in class from the build log (20), peer assessment (10)

Build goal: none. The product is frozen 24 hours before.

Demo Day (150 min). Each team has 10 minutes plus 5 of questions in front of a panel (instructor plus two invited managers or alumni): live demonstration of the product with a user story, the problem and value hypothesis, evidence from the test set, the risk memo’s main findings, the build / buy / vibe decision and a roadmap to production. The deck is generated with AI and its use is declared. The class grades with the rubric; the panel’s grade counts.

Strategy revisited (30 min). What remains a moat when building is cheap (proprietary data, distribution, workflow integration, earned trust); organizational implications of citizen developers and how to govern them; the personal AI work system each student keeps after the course: a library of skills, trusted connectors, one automation with an owner and a log.

Reflection (30 min). Individual reflection memo, drafted before class and finished in class from the build log: what the AI did, what I decided, where it misled me, what I would do differently, and how this changes my work with technology teams. Peer assessment within teams.
